## Comments

**Реализация (ветка `slice/03-guest-posts-comment`).** Внешний цикл: SMOKE-01 и E2E-01 (написан в срезе 02). `make check` проходит lint, unit (покрытие PHP 100%), smoke и regression и падает только на E2E-01, шаг 5: индикатора WS ещё нет. CI на GitHub в этом срезе не запускался, ветка не запушена.

Отклонения от плана. Все они внесены в `docs/test-plans/` в этом же срезе:
- `CommentForm`: поля `mixed`, а не `string`. Поле может прийти массивом или не прийти (CF-05, REG-G-19), тип проверяет валидатор. `formName()` пустой: поля формы `name` и `text` без обёртки, как в REG-G-19 (`name[]=x`). Форма нормализует строки в `beforeValidate`, поэтому при ошибке форма показывает введённое значение уже без пробелов по краям.
- `PlainTextValidator` сам проверяет обязательность (пустая строка → `name.required`, `text.required`) и не пропускает пустое (`skipOnEmpty = false`). Порядок ошибок в UNIT-VAL-09 дополнен обязательностью, как в `messages.md`.
- Новый UNIT-CF-06 (подписи полей из каталога): покрытие PHP считается по приложениям, и `attributeLabels` формы из `common` не покрывали тесты `common`.
- `CommentService` — final readonly, поэтому тесты `frontend\controllers\CommentController` работают с настоящим сервисом и мокают его границы: репозиторий, часы, лимит. «Сервис не вызывается» = «репозиторий не получил `create`». Пояснение добавлено в раздел FC плана.
- Конструктор `frontend\controllers\CommentController` без `$config`: иначе 6 параметров при лимите 5.
- REG-G-12 разбит на два метода: «чужой» токен — токен админки, «протухший» — токен, выданный до смены CSRF-cookie.
- REST-regression публичной части: `postComment()` собирает тело формы сама (`http_build_query`), потому что модуль REST кодирует массив параметров в JSON для лога и падает на невалидном UTF-8 (REG-G-18). Ответ на POST проверяется через `seeResponseContains`: crawler PhpBrowser после `sendPost` остаётся на предыдущей странице. По той же причине `TestSeed` кодирует набор провайдера с `JSON_INVALID_UTF8_SUBSTITUTE`.
- `ActiveRecordCommentRepository::create` пишет `created_at` с микросекундами (UNIT-REPO-01 дополнен). REG-G-20 поймал, что комментарий из формы с меткой до секунды встаёт ниже фикстур той же секунды.
- Сессия публичной части получила своё имя cookie `comments-public` (REG-G-31).

Что осталось открытым:
- `SVC-01` пока без публикации события `comment.created`: её добавляет срез 05.
- Повторный прогон regression на том же стенде без `make stand-down` по-прежнему падает на уникальном логине админа из фикстуры (см. тикет 02). `make check` поднимает свежий стенд, там проблемы нет.

**Правки после ревью среза.**

Исправлено:
- REG-G-31 больше не отправляет форму и не сбрасывает лимит (ярус `parallel`): сессию открывает `GET /`. Имя cookie сессии вынесено в `common\web\SessionCookie::PUBLIC_SITE`, его читают конфиг публичной части и тест.
- REG-G-10, REG-G-12: ровно одно действие и три блока. Чтение ленты после POST (REG-G-10, REG-G-20) — это проверка результата, а не второе действие: правило записано в `regression.md`, «Проверка через ленту». Для Arrange REG-G-12 добавлен шаг `grabCsrfTokenAt()`: Rector (`NewlineBeforeNewAssignSetRector`) требует пустую строку перед присваиванием после вызова, а она разбивала Arrange на два блока.
- Адреса стенда в REG-G берутся из `PUBLIC_URL` и `ADMIN_URL` (`publicUrl()`, `adminUrl()`, `adminHost()`). В REG-A среза 02 адреса по-прежнему записаны строкой, это вне среза.
- REG-G-03: «средняя дата» названа (`$betweenOldestAndNewest`, шаг `createdAtBetween()`).
- UNIT-REPO-02 проверяет только null, как в плане. UNIT-FC-02 проверяет порядок: невалидный POST при исчерпанном лимите получает 429, а не 422 (при обратном порядке тест падает с 422). В примечании к разделу FC плана добавлен мок лимитера.
- REG-G-04: `?page[]=1` отвечал 400. Добавлен в провайдер (красный тест), параметр `page` у `actionIndex` теперь без типа, массив → первая страница. План G-04 дополнен.
- `PlainTextValidator`: у `min` и `max` нет умолчаний, без них `init()` бросает `InvalidConfigException` (новый UNIT-VAL-10). Раньше `max = 1` молча отклонял ввод длиннее символа.
- `resetCommentLimit()` перебирает ключи через `SCAN`, а не `KEYS`.
- `<time>` в ленте получил атрибут `datetime` (ISO 8601).

Оставлено (решение за человеком):
- `white-space: pre-line` в ленте: так требует `unit.md`, «Как показывается текст». UNIT-NORM-04 говорит о сохранённом тексте, а не об отображении. Если подряд идущие пробелы должны быть видны, это правка плана для ленты и админки сразу (`pre-wrap`).
- `"Ян\r\nЯн"` в имени → `name.invalid_chars`, а не `name.multiline`. По плану `\r` — управляющий символ, а замена `\r\n` → `\n` (NORM-03) есть только у текста. Код ответа 422 верный, однострочное поле браузера `\r` не отправит. U+2028/U+2029 внутри имени проходят как однострочные: обрезаются только по краям.
- `CommentForm` нормализует строки в `beforeValidate`, а `getNormalized*` нормализуют ещё раз. Нормализация идемпотентна, на поведение не влияет. Убрать повтор — значит менять интерфейс формы и тесты CF.
- Формат ключа лимита (`rate-limit:` + `comment:` + IP) собран в лимитере, контроллере и тестовом шаге сброса. Стоит отдать ключ одному владельцу, когда лимит понадобится ещё где-то.
- Границы 2/64/2000 повторяются в текстах каталога. Параметр в сообщении требует правки `messages.md` и MSG-01.
- Лимит считается по `REMOTE_ADDR`, `trustedHosts` не задан, как требует спека. Если перед nginx появится балансировщик, все гости попадут в одно окно. Ограничение стоит записать в ADR.
- `created_at` ставит PHP (`NativeClock`), а К0 в E2E-01 берёт `now()` из БД: два источника часов. На одном хосте это безопасно.
