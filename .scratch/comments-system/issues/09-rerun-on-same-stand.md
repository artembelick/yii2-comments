# 09: Повторный прогон на том же стенде (ИЗ-1)

**What to build:** тесты стенда (smoke, regression, REG-WS, e2e) проходят при повторном запуске на том же стенде, без `make stand-down`. Сейчас это нарушает правило ИЗ-1 из `docs/test-plans/rules.md` («в любом количестве повторов»), а `make check` скрывает нарушение, потому что каждый раз поднимает свежий стенд.

**Blocked by:** 08.

**Status:** done

## Что сейчас ломается

1. **Метки повторяются между прогонами.** Seed Faker вычисляется из имени теста (ДТ-2: `common/tests/_support/TestSeed.php`, `e2e/support/faker.ts`), а метка берётся из того же Faker (`FixtureFactory::tag()`, `uniqueTag()` в `e2e/support/factories.ts`). Второй прогон создаёт админа с тем же логином `admin-xxxx` и падает на уникальном индексе. С комментариями ещё хуже: тест находит по метке и свои строки из прошлого прогона, и проверки вида «ровно одна строка» или «первая в ленте» становятся ложными. Записано в тикетах 02, 03 и 04.
2. **Ярус `pristine` требует пустую БД** (REG-G-02, REG-A-32). Во втором прогоне БД уже заполнена.
3. **`make admin` не идемпотентен:** повторный вызов на том же стенде падает с `cli.admin.username_taken`, а `make check` и CI вызывают его перед smoke.
4. **Ночной двойной прогон ничего не проверяет по ИЗ-1:** в CI это два отдельных job, у каждого свой свежий стенд (`.github/workflows/ci.yml`, job `nightly`). Он ловит зависимость от порядка, а не от повтора.

## Решения

Предложены по умолчанию. Если человек правит их до старта, правка идёт сюда, в `rules.md` и в `docs/test-plans/README.md`.

- **Метка = id прогона + часть из Faker.** `TEST_RUN_ID` — короткая случайная строка, одна на весь прогон и на все воркеры Playwright и процессы Codeception. Makefile генерирует её, если она не задана, печатает в начале прогона и передаёт в контейнеры. Данные теста по-прежнему определяются seed из имени (ДТ-2), меняется только префикс метки. Чтобы воспроизвести падение, передают тот же `TEST_RUN_ID` и `SEED` из отчёта, на свежем стенде.
- **Метка длиннее.** Сейчас 4 символа `[a-z0-9]`: около 1,7 млн вариантов. С фиксированным seed совпадение либо есть всегда, либо нет никогда, но с id прогона на ~300 тестов шанс случайной коллизии за прогон около 3%. Нужно 8 символов (4 от прогона, 4 от Faker) или больше. Проверить, что метка влезает в ограничения: имя автора до 64 символов, логин до 64.
- **`pristine` не повторяется на заполненной БД.** `make test-regression-pristine` сам пересоздаёт БД стенда (drop schema + миграции) перед ярусом: он и так идёт первым. Исключение из ИЗ-1 для этого яруса записывается в `rules.md` прямо в строке ИЗ-1, со ссылкой на «Ярусы».
- **`make admin` идемпотентен:** если админ из `.env.test` уже есть, цель ничего не делает и выходит с 0. Пароль при этом не меняется: smoke должен работать и на стенде, где данные трогать нельзя. Делается в Makefile проверкой существования, а не новым флагом команды `admin/create`.
- **Тесты `exclusive`, которые смотрят на начало ленты или списка,** вставляют свои комментарии с самыми новыми датами (уже так). Проверить, что ни один из них не считает строки без фильтра по метке: старые строки прошлого прогона не должны менять результат.

### Решения человека после ревью

Ревью нашло в плане противоречия; человек решил их так (внесено и в `rules.md`, `docs/test-plans/README.md`).

- **Ручная проверка — повтор без `pristine`.** «Дважды `make test-regression`» не проверяет повтор: второй regression начинается с `pristine`, а тот пересоздаёт БД. Вместо этого на одном стенде два раза подряд идут regression без яруса `pristine` (`parallel`, `exclusive`, REG-WS) и e2e: цель `make test-no-pristine`.
- **`make test-rerun` проверяет идемпотентность `make admin`.** В первом проходе порядок `pristine` → `admin` → smoke → остальное, чтобы `pristine` не стирал админа и `make admin` второго прохода шёл по ветке «уже есть».
- **Падение второго прохода воспроизводится через `make test-rerun`.** Id второго прохода задаётся снаружи (`TEST_RUN_ID_2`, генерируется, если не задан), `make test-rerun` печатает оба id и seed. Падение второго прохода воспроизводят `TEST_RUN_ID=<1> TEST_RUN_ID_2=<2> SEED=<1> make test-rerun`, а не на свежем стенде (ДТ-2).
- **В CI `TEST_RUN_ID` один на job.** Каждый шаг `run: make …` — отдельный вызов make, поэтому id генерируется первым шагом job и передаётся следующим через `$GITHUB_ENV` (следует решению «одна на весь прогон»).

## Внешний цикл (пишется первым)

- Новая цель `make test-rerun`: поднять стенд, прогнать smoke → regression → REG-WS → e2e, затем ещё раз всё, кроме `pristine`, на том же стенде без `stand-down`, с другим `TEST_RUN_ID` и другим seed порядка. Второй проход должен быть зелёным. Сейчас он красный на уникальном логине: красное состояние зафиксировать в комментарии к тикету.
- Job `nightly` в CI переходит на `make test-rerun` вместо двух `make check` с разными seed (или дополняется им). Двойной `make check` с разными seed из тикета 10 остаётся отдельной проверкой порядка.

## Внутренний цикл (TDD, по одному тесту)

- UNIT-FIX-02 дополняется: при одном seed и разных `TEST_RUN_ID` метки разные, при одном seed и одном `TEST_RUN_ID` одинаковые.
- Новый UNIT-FIX-03: метка состоит из id прогона и части из Faker, длина и алфавит как в решении. Без `TEST_RUN_ID` фикстура падает с понятным сообщением, а не берёт пустую строку.
- То же для `e2e/support/factories.ts`: тест на `uniqueTag` в Vitest (новый ID в `unit.md`, раздел про поддержку e2e) и проверка в E2E-FIX-01, что метки фабрик и PHP-фикстур собираются по одному правилу.
- Документы: `rules.md` (ИЗ-1, ДТ-2: как воспроизвести по `TEST_RUN_ID` и `SEED`), `docs/test-plans/README.md` («Работа с данными», «Ярусы», «Запуски»: новая цель и nightly).

## Комментарии

**Красное состояние внешнего цикла.** Первый `make test-rerun` (до правок): проход 1 зелёный целиком, проход 2 упал сразу на `make admin` — «Логин smoke-admin уже занят.» (`cli.admin.username_taken`). Дальше второй проход не дошёл; повторяющиеся метки `admin-xxxx` закрыты UNIT-FIX-02 и UNIT-E2E-TAG-01, которые были красными до кода.

**Как сделано.**
- Метка — 8 символов `[a-z0-9]`: `TEST_RUN_ID` (4) + 4 из Faker. Логин `admin-` + 8 = 14 символов, имя автора — имя из Faker + пробел + 8, оба укладываются в 64.
- PHP: `FixtureFactory` принимает id прогона вторым аргументом конструктора и падает `InvalidArgumentException` с подсказкой про `TEST_RUN_ID`, если он пустой или не из 4 символов `[a-z0-9]`. `FixturesModule` берёт его из окружения и пишет в отчёт о падении рядом с `faker-seed` (`test-run-id`).
- TS: `uniqueTag(faker, runId = process.env.TEST_RUN_ID)` с той же проверкой; фикстура `faker` добавляет аннотацию `test-run-id`. Vitest для хелперов e2e — новый проект `e2e-support` (`e2e/support/__tests__`), путь добавлен в `tools/checks/test-locations.js`, чтобы сверка ID видела эти тесты. E2E-FIX-01 дополнен тестом, что логин из фабрики — `admin-` + `TEST_RUN_ID` + 4 символа.
- Makefile: `TEST_RUN_ID` генерируется из `/dev/urandom`, если не задан, печатается для целей `check` и `test-*` и экспортируется во вложенные make и в контейнеры (`-e TEST_RUN_ID=…` у `exec php` и `run playwright`). `make admin` сначала проверяет логин через `psql` в контейнере postgres и при наличии ничего не делает. `make test-regression-pristine` перед ярусом делает `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` и миграции. `make test-rerun` — два прохода с разными `TEST_RUN_ID` и seed.
- CI: добавлен job `nightly-rerun` (`make test-rerun`) рядом с прежним двойным `make check`.
- Тесты `exclusive` просмотрены: строки без фильтра по метке нигде не считаются (лента и список сверяются по своим текстам или по навигации пагинатора), правки не понадобились — второй проход это подтвердил.
