# 11: Готовность к ревью

**What to build:** проект готов к отправке. Страница отчёта на GitHub Pages показывает результаты прогона, покрытие, применённые методики и стек. README коротко объясняет запуск и ведёт на неё. Путь одного комментария можно показать шаг за шагом с тестом на каждом шаге.

**Blocked by:** 06, 07, 08, 09, 10.

**Status:** ready-for-human

## Страница отчёта

Решения приняты на гриллинге.

**Хостинг и сборка:**
- GitHub Pages. Публикуется из CI после каждого push в `main` (шаги `actions/upload-pages-artifact` и `actions/deploy-pages`, у job права `pages: write` и `id-token: write`). Один раз вручную: Settings → Pages → Source: «GitHub Actions». Это делает человек.
- В PR отчёт не публикуется: собранный сайт лежит артефактом job, его можно скачать из прогона.
- Результаты шардов `parallel` и job `serial` сводит в один отчёт отдельный job `report` после них. Он же собирает главную страницу. Локально то же собирает цель `make report`.

**Отчёт о прогоне: Allure.**
- Адаптеры для всех трёх раннеров: `allure-codeception` (unit и REST-regression), `allure-vitest` (unit JS), `allure-playwright` (smoke, REG-WS, e2e). Существующие JUnit-репортёры остаются: на них работают `tools/checks junit` и CI.
- Шаги `test.step` из Playwright видны в отчёте как шаги, trace и скриншоты падений приложены. Тесты сгруппированы по набору (unit, smoke, regression, e2e) и по ID.
- Истории прогонов нет: каждый прогон на `main` даёт свежий отчёт.
- Версию Allure (2 или 3) выбирает реализатор: та, у которой сборка отчёта проще встаёт в контейнер `node`.

**Главная страница** (`site/`, статическая, русский язык, названия инструментов как есть). Разделы, у каждого пункта одна-две ссылки на настоящие тесты:
1. **Итог прогона:** число тестов по наборам, прошло и упало, коммит и время прогона, ссылка в Allure.
2. **Покрытие кода:** строки PHP (pcov), строки и ветки JS (v8), ссылки на HTML-отчёты покрытия с разбивкой по файлам.
3. **Покрытие требований:** доля сценариев из `docs/test-plans/`, реализованных в тестах (из сверки ID), и матрица пути P1–P13 → ID тестов со ссылками.
4. **Пирамида и наборы:** unit, smoke, regression, e2e: зачем каждый, как работает, когда запускается локально и в CI, как масштабируется. Double-loop TDD по вертикальным срезам (ADR 0001).
5. **Техники тест-дизайна:** граничные значения (2/64/65, 2000/2001), классы эквивалентности (провайдеры невалидных данных), таблица решений (порядок ошибок валидации), переходы состояний (комментарий активен ⇄ удалён, состояния WS-соединения).
6. **Трассируемость и проверка тестов:** сверка ID в обе стороны, проверка тестов мутациями из комментариев к тикетам 05–10.
7. **Стабильность и правила:** ярусы, уникальные метки, seed, запрет sleep, retries 0, двойной и повторный прогон (тикет 09), коротко `rules.md`.
8. **Стек:** Yii2, PHP, Postgres, Redis, Workerman, Docker, Codeception, Vitest, Playwright, Allure, линтеры, GitHub Actions.
9. **Вне объёма:** нагрузочные тесты, заголовки безопасности, матрица браузеров, мутационное тестирование инструментом. Одной фразой: осознанно не делали.

- Ссылки на тесты, планы и ADR ведут на файлы GitHub по SHA коммита прогона, а не на `main`: так они не ломаются после следующих правок.
- Цифры (итог, покрытие, доля сценариев) подставляются при сборке из результатов прогона. Руками в странице их нет.
- Подробные объяснения живут только на странице. README их не повторяет, чтобы не держать две копии.

## Комментарии

**Как сделано.**
- **Тест-планы до кода.** `docs/test-plans/README.md`: сверка ID в обе стороны, Allure во всех раннерах и группы отчёта, `make report` и `tools/report`, job `report` и `pages`, тесты `tools/report/__tests__`. Новых ID нет: тесты своих инструментов ID не несут (как `tools/checks`).
- **Allure 3** (`allure` из npm, конфиг `allurerc.js`): собирается в контейнере `node` без Java, Allure 2 потребовал бы JRE. `historyPath` не задан, истории нет. Дерево — `groupBy: parentSuite, suite, subSuite`.
- **Адаптеры.** `allure-codeception` — расширение в корневом `codeception.yml`. Адаптер считает `outputDirectory` от output каждого приложения (`common/tests/_output` и т. д.) и срезает ведущий `/`, поэтому путь `../../../tests/_output/allure-results`. `allure-vitest` — репортёр в `vitest.config.js`, `allure-playwright` — в `e2e/playwright.config.ts`: шаги `test.step`, trace и скриншоты падений приходят вложениями. JUnit-репортёры на месте. Все пишут в `tests/_output/allure-results`, `make check` и `make test-rerun` чистят каталог в начале.
- **`tools/report`** (TDD, `tools/report/__tests__`, покрытие 100%). Готовит результаты: имя PHP-теста — из `TestDox` или первой строки docblock метода (адаптер пишет имя метода), группы «набор по префиксу ID → ID», тесты без ID — в unit, группа «Тесты инструментов». У наборов data provider Codeception одно имя и один `historyId` без параметров: Allure счёл бы их повторами одного теста, поэтому каждый получает номер набора. Затем страница из шаблона `tools/report/page.html`: итог по наборам, коммит и время начала прогона (первый результат), покрытие PHP из clover и JS из json-summary, доля реализованных сценариев и матрица P1–P13 из `docs/test-plans/README.md` (диапазоны и семейства ID раскрываются по плану). Ссылка на несуществующий файл (`{{file:…}}`), нереализованный ID (`{{test:…}}`) или ID матрицы вне плана роняет сборку: битой ссылки на странице не будет. Нет отчёта покрытия — «нет данных».
- **`make report`**: `tools/report` → `allure generate` → HTML покрытия (`--coverage-html` у Codeception, `lcov-report` у Vitest) в `site/coverage/`. `site/` в `.gitignore`. Ссылки — по SHA: локально `git rev-parse HEAD` и `git remote get-url origin`, в CI `REPORT_SHA` (head-коммит PR, а не merge-коммит, или `github.sha`) и `REPORT_REPO`.
- **Сверка ID в обратную сторону** — в `tools/checks` (правило `test-ids`): ID реализован, если с него начинается имя теста (строка JS, `TestDox`, первая строка docblock Cest), упоминание в комментарии не считается. Каркас с `--allow-empty` её пропускает. Итог: 315 из 315.
- **CI.** Job `report` (`needs: unit, parallel, serial`, `if: always()` на PR и push в `main`): скачивает артефакты `reports-*`, складывает Allure-результаты в один каталог, покрытие берёт из `reports-unit`, `make report`, артефакт `site`; на push в `main` ещё `upload-pages-artifact`. Публикует отдельный job `pages` (`deploy-pages`, права `pages: write` и `id-token: write`, environment `github-pages`) только на push в `main`: environment `github-pages` по умолчанию пускает только `main`, в PR job с ним упал бы. `actionlint` на машине нет, workflow сверен вручную (YAML разобран, условия и `needs` проверены).
- **README** сокращён до запуска, трёх команд, строки на набор и ссылки на страницу. Ярусы, seed, повтор падений и правила живут на странице и в `docs/test-plans/`.

**Красные фазы и мутации.**
- Сверка: тесты `implementedIds` и `unimplementedPlanIds` красные до кода (функций нет); CLI-тест на дереве `unimplemented` — красный: код 0 вместо 1. Мутация на репозитории: имя SMOKE-04 начато не с ID → `test-ids: docs/test-plans/smoke.md:13 SMOKE-04 из плана не реализован…` (плюс прямая сторона: тест без ID), после отката нарушений нет.
- `tools/report`: каждый модуль начинался с теста, красного на отсутствии модуля.
- Дефект, найденный первой сборкой на настоящем прогоне: 9 Cest-тестов regression и часть unit-тестов ушли в «Тесты инструментов». Имя бралось из первого docblock перед методом: у unit-тестов с `TestDox` это был docblock с `@param`, у Cest — docblock константы выше. Тест на это был красным; теперь имя — из `TestDox` метода или из его собственного docblock, все 624 PHP-результата получили имя с ID.

**Наблюдения.**
- Allure 3 грузит данные отчёта через `fetch`: `site/allure/` смотреть через http (`python3 -m http.server -d site`), главную `site/index.html` можно открыть и файлом. Проверено локально через http-сервер: главная с разделами 1–9, отчёт Allure с деревом «набор → ID», HTML покрытия.
- Номер набора data provider в Allure — порядковый в этом прогоне (Codeception не пишет имя набора), при случайном порядке он от прогона к прогону разный.
- Локальный `npx vitest run …` вне `make check` дописывает результаты в `tests/_output/allure-results`; `make check` чистит каталог.

**Проверка.** `make check` зелёный целиком три раза: `SEED=11111` (`TEST_RUN_ID=c256`, до исправления имён PHP-тестов в `tools/report`), затем на итоговом коде `SEED=22222` (`oplj`) и `SEED=33333` (`bity`). Оба итоговых прогона дали одинаковый результат: unit PHP 411 и JS 381, smoke 4, regression `pristine` 3, `parallel` 106, `exclusive` 104, REG-WS 19 + 5, e2e 2 + 8; покрытие PHP 625/625 строк, JS 666/666 строк и 264/264 веток; сверка ID 315 из 315. `make report` после каждого прогона собрал `site/` с разделами 1–9: страницы обоих прогонов совпадают по итогу (1043 из 1043 по наборам unit 792, smoke 4, regression 237, e2e 10) и покрытию. CI проверится после пуша ветки: job `report` в PR и артефакт `site`; публикация — после слияния в `main`.

**Осталось человеку.**
1. Включить Pages: Settings → Pages → Source: «GitHub Actions». Pages с приватного репозитория требует платного плана: репозиторий для этого должен быть публичным.
2. Запушить ветку, проверить CI в PR: job `report` зелёный, в прогоне есть артефакт `site`, страница из него открывается.
3. Провести `/code-review` среза и отметить по его итогам.
4. После слияния в `main`: jobs `report` и `pages` зелёные, страница открывается по ссылке Pages. В README стоит адрес по умолчанию для проекта, https://artembelick.github.io/yii2-comments/; если Pages выдаст другой (свой домен), поправить README.
5. Отметить «На чистой машине `make check` зелёный, CI на `main` зелёный» после зелёного CI на `main`.
6. Ручной проход P1–P13: на каждом шаге открыть тест из матрицы раздела 3 страницы.
7. Опубликовать репозиторий и отправить ссылки на репозиторий и на страницу отчёта.
