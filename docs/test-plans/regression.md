# Regression

**Зачем:** зафиксировать контракты, которые не должны ломаться при любых изменениях: валидацию, права, безопасность, идемпотентность. Сюда же добавляется тест на каждый найденный баг.
**Как:** две части.
- **REST** (Codeception, PhpBrowser/REST): HTTP-запросы к тестовому стенду без браузера. Разделена на гостевые (REG-G) и админские (REG-A) действия.
- **WS-контракты** (Playwright-раннер, Node-клиент `ws`, без браузера): REG-WS.

**Когда:** в `make check` после smoke, до e2e. В CI на каждый PR, всегда целиком.
**Данные** (подробно в [README](README.md#работа-с-данными)):
- БД не очищается;
- админы (в том числе заблокированный) и комментарии-предусловия создаются Yii-фикстурами на лету, с уникальной меткой, без выгрузки;
- варианты входных данных задают data provider'ы, один именованный набор на проверку.

**Ярусы:**

| Ярус | Сценарии |
|---|---|
| `pristine` | G-02, A-32 |
| `exclusive` | G-03, G-04, G-05, G-07, G-10…G-23, A-30, A-31, A-50, A-52, A-61, A-70, A-71, WS-06, WS-07 |
| `parallel` | Все остальные |

**Правила валидации, общие для всех частей:**

| Поле | Допустимо | Ограничения |
|---|---|---|
| Имя | 2–64 символа | Одна строка |
| Текст | 1–2000 символов | Переносы разрешены, `\r\n` → `\n` |

- Длина считается после обрезки пробелов по краям, в символах Unicode.
- Управляющие символы (кроме `\n` в тексте), табуляция и невалидный UTF-8 → ошибка.
- При ошибке валидации ответ 422 и форма с введёнными значениями.

**Проверка через ленту:** результат отправки формы (флэш, комментарий первым в ленте) проверяется открытием ленты в блоке Assert (`grabFeedTexts`). Это чтение результата единственного действия, а не второе действие (ЧТ-2): ответ на POST — редирект, и показанное в ленте видно только следующим GET.

**Баги:** тест `REG-BUG-NNN`, в описании ссылка на тикет в `.scratch/`.

**ID:** в таблицах ниже ID записаны коротко внутри своего раздела. Полный ID в имени теста: `G-13` → `REG-G-13`, `A-08a` → `REG-A-08a`, `WS-01` → `REG-WS-01`.

### События

Проверяются подписчиком на канал Redis внутри REST-теста (`common/tests/_support/RedisChannelProbe`). «Ровно одно» и «нет» проверяются без ожидания по времени: после действия тест публикует в канал метку, и события действия — всё, что пришло до неё. Событие создания вызывает гость, поэтому A-70 и A-71 для создания лежат в `frontend/tests/regression`.

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| A-70 | Провайдер действий: создание, правка, удаление, восстановление | Ровно одно событие нужного типа с полным комментарием |
| A-71 | Провайдер: невалидная отправка, отказ по rate limit, правка без изменений, повторное удаление или восстановление | Событий нет |

## WS-контракты (REG-WS)

**Протокол:**
- **Сообщения клиента:** только `{type: "auth", token}` (первым сообщением) и `{type: "ping"}`.
- **Сообщения сервера:**
  - `{type: "auth.ok"}`;
  - `{type: "pong"}`;
  - события `{type: "comment.created" | "comment.updated" | "comment.deleted" | "comment.restored", comment: {…}}`.

**Коды закрытия:**

| Код | Значение | Что делает клиент |
|---|---|---|
| 4400 | Нарушение протокола | Переподключается с backoff |
| 4401 | Нет авторизации или токен неверен | Берёт новый токен. Если токен не выдали (401), уводит на логин |
| 4403 | Сессия завершена: logout или блокировка | Сразу уводит на логин, не переподключается |
| 1006, 1001 и прочие | Разрыв | Переподключается с backoff |

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| WS-01 | Handshake с чужим `Origin` | HTTP 403, соединение не открыто |
| WS-02 | Нет `auth` 5 секунд | Закрыто с кодом 4401 |
| WS-03 | Провайдер: неверный токен, пустой токен, токен другого формата | Закрыто 4401 |
| WS-04 | Токен использован, затем второе соединение с тем же токеном | Второе закрыто 4401 |
| WS-04a | Второе соединение с тем же токеном отклонено, затем `ping` по первому | `pong`: первое соединение живо |
| WS-05 | Провайдер: не-JSON, неизвестный `type`, `ping` до авторизации, повторный `auth` после `auth.ok`, сообщение больше 4 КБ | Закрыто 4400 |
| WS-06 | Открытое, но неавторизованное соединение; в это время создаётся комментарий | Событий не получает |
| WS-07 | Авторизованное соединение; провайдер действий: создание, правка, удаление, восстановление | Ровно одно событие нужного типа; `comment` содержит `id`, `author`, `text`, `status`, `createdAt`, `updatedAt`, `updatedBy`, `deletedBy` |
| WS-08 | Соединения: Админ 1 в сессии 1, Админ 1 в сессии 2, Админ 2. Logout сессии 1 | Закрыто только соединение сессии 1 с кодом 4403 |
| WS-09 | Соединения Админа 1 в двух сессиях и Админа 2. Админа 1 блокируют (эффект `admin/block`, см. ниже) | Оба соединения Админа 1 закрыты 4403, соединение Админа 2 живо |
| WS-10 | `ping` после авторизации | `pong` |
| WS-11 | Провайдер: токен выдан, затем logout этой сессии; токен выдан, затем смена пароля админа (эффект `admin/password`, см. ниже). После этого `auth` этим токеном (в пределах TTL) | Закрыто 4401, `auth.ok` не приходит |
| WS-12 | Авторизованное соединение Админа 1. Админ 1 заблокирован в БД, а `access.revoked` до WS-сервера не дошёл (сообщение не публикуется). Затем `ping` | Закрыто 4403, `pong` не приходит: доступ перепроверяется на каждом `ping` |

Контейнер Playwright без PHP и не может запустить `./yii`, поэтому WS-09 и WS-11 повторяют эффект консольных команд так, как его видит WS-сервер (`e2e/support/accounts.ts`): `admin/block` — статус «заблокирован» и новый `auth_key` в БД и `access.revoked` в `ws.control`, `admin/password` — новый `auth_key` в БД и `access.revoked`. Сами команды запускают на стенде REG-A-09b и A-09c и проверяют, что команда действительно публикует в `ws.control` то сообщение, которое WS-09 и WS-11 подставляют из Node (форма сообщения, `userId` числом, DI консоли). Порядок «сначала БД, потом публикация» — UNIT-ACC-05 и ACC-07.

Истечение токена (TTL 60 секунд) проверяется в unit.
