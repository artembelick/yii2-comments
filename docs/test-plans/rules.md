# Правила написания автотестов

Правила обязательны для всех наборов: unit (Codeception, Vitest), regression, smoke, e2e. Где правило можно проверить автоматически, это делает линтер (колонка «Контроль»). Остальное проверяется на `/code-review` каждого среза.

## 1. Изоляция

Тест не зависит ни от других тестов, ни от порядка их запуска, ни от машины.

| # | Правило | Контроль |
|---|---|---|
| ИЗ-1 | Тест проходит, если запустить его один, в любом порядке и в любом количестве повторов | `make check` перемешивает PHP-тесты (Codeception с `--seed`) и Vitest (`sequence.shuffle`). Seed печатается, упавший прогон повторяется с тем же seed. Playwright случайный порядок не поддерживает: для него независимость держится на уникальных метках и ярусах (ИЗ-3), а ночной CI прогоняет всё дважды |
| ИЗ-2 | Тест не опирается на данные или состояние, которые оставил другой тест. Всё нужное он создаёт сам: фикстурой, фабрикой или через Arrange | Ревью |
| ИЗ-3 | На стенде тест работает только со своими данными, помеченными уникальной меткой. Тесты на глобальное состояние живут в ярусах `pristine` и `exclusive` | Ревью |
| ИЗ-4 | Тест возвращает на место всё глобальное, что поменял: env, DI-контейнер Yii, статические свойства, `Yii::$app`, глобалы JS. В Vitest это `unstubEnvs` и `restoreMocks`, в PHP — сброс контейнера в `_after` | Конфиг раннеров |
| ИЗ-5 | Unit-тест не ходит в сеть, БД, Redis и файловую систему. Исключения: тесты репозиториев, AR и фикстур (UNIT-FIX) работают на тестовой Postgres внутри транзакции с откатом, а сверка каталога сообщений (UNIT-MSG-01) читает сами файлы каталога | Ревью |
| ИЗ-6 | Между тестами нет общего изменяемого состояния: никаких полей класса, заполненных в одном тесте и прочитанных в другом, и никаких модульных `let`, которые тесты меняют | oxlint, ревью |

## 2. Детерминизм

Один и тот же код даёт один и тот же результат при любом запуске.

| # | Правило | Контроль |
|---|---|---|
| ДТ-1 | Реального времени в тестах нет. В PHP время приходит через `ClockInterface` с замороженными часами, в JS — через `vi.useFakeTimers()`. Процессы работают в `TZ=UTC` | Линтер: запрет `time()`, `date()`, `new DateTime()` без аргумента, `Date.now()` в тестах |
| ДТ-2 | Случайность только с фиксированным seed. Faker получает seed, вычисленный из ID теста, поэтому повторный прогон даёт те же данные. Seed виден в сообщении о падении | Хелпер фабрик |
| ДТ-3 | Фиксированных ожиданий нет: никаких `sleep`, `usleep`, `waitForTimeout`. Ждём условие: автоожидание Playwright, `expect.poll`, `toPass` с таймаутом | Линтер |
| ДТ-4 | Тест не зависит от порядка элементов, если этот порядок не гарантирован контрактом. Порядок проверяется только там, где он часть поведения (лента, список) | Ревью |
| ДТ-5 | Внешней сети нет. Все адреса указывают на тестовый стенд | Конфиг стенда |
| ДТ-6 | Повторов нет (`retries: 0`). Нестабильный тест считается багом: его чинят, а не перезапускают | Конфиг Playwright |

## 3. Читаемость

Тест — это документация поведения. Человек, не видевший кода, понимает из теста, что проверяется и почему.

| # | Правило | Контроль |
|---|---|---|
| ЧТ-1 | Имя теста — это ID из тест-плана и поведение на русском: `REG-G-13: имя короче 2 символов отклоняется`. Для провайдера у каждого набора своё имя: `имя из 1 символа → name.too_short`. В PHP имя метода не вмещает ID и русский текст, поэтому имя теста записывается рядом с методом: в unit — в `#[TestDox('UNIT-…: …')]`, в Cest — первой строкой docblock метода (`/** REG-A-01: … */`). Метод при этом называется по поведению на английском | Сверка ID: проверяет ID в TestDox или docblock |
| ЧТ-2 | Структура Arrange → Act → Assert (Дано → Действие → Проверка), три блока разделены пустой строкой. Действие ровно одно | Ревью |
| ЧТ-3 | Один тест проверяет одно поведение. Несколько проверок допустимы, если все они описывают результат одного действия | Ревью |
| ЧТ-4 | В теле теста нет логики: никаких `if`, циклов, `try/catch` и тернарных операторов. Варианты задаются через провайдер, ожидаемое исключение — через `expectException` или `toThrow` | Линтер (`vitest/no-conditional-in-test`, свои правила для PHP) |
| ЧТ-5 | В Arrange видно только то, что важно для поведения. Остальное получает умолчания фабрики. Значимые значения названы: `$tooShortName = 'Я'` | Ревью |
| ЧТ-6 | Хелперы убирают шум (вход, создание данных), но не прячут действие и проверку. Читатель видит, что делается и что ожидается, прямо в тесте | Ревью |
| ЧТ-7 | Тексты интерфейса и сообщений берутся из каталога `messages.json`, а не пишутся в тесте строкой. Исключение — тест выбора формы ICU plural (UNIT-JS-FMT-02): ожидание, собранное из шаблона каталога тем же разбором, повторило бы код и прошло бы при любой ошибке выбора формы, поэтому формы там записаны литералами | Ревью |
| ЧТ-8 | Тест-файл до 500 строк, один файл — один класс или один сценарий плана | Линтер (лимиты) |

## 4. Проверки

Тест ловит настоящие поломки и не ломается от рефакторинга.

| # | Правило | Контроль |
|---|---|---|
| ПР-1 | Проверяется наблюдаемое поведение и контракт (результат, ответ, состояние, событие), а не внутреннее устройство | Ревью |
| ПР-2 | Моки только на границах: репозитории, Redis, публикатор, часы, сеть, соединения Workerman. Тестируемый класс, value-объекты и формы не мокаются | Ревью |
| ПР-3 | Взаимодействие с моком (`expects(once())`, `toHaveBeenCalledWith`) проверяется только тогда, когда оно и есть поведение: опубликовано событие, вызван `close(4403)` | Ревью |
| ПР-4 | Проверки точные: `assertSame` вместо `assertEquals`, `toStrictEqual` и `toBe` вместо `toBeTruthy`, полный ожидаемый объект вместо отдельных полей там, где важен весь контракт | Линтер (strict-rules, правила vitest) |
| ПР-5 | В каждом тесте есть хотя бы одна проверка | PHPUnit strict, `expect.hasAssertions()` |
| ПР-6 | Проверка отсутствия идёт в паре с доказательством, что искали в правильном месте. Например, «удалённого нет в ленте» проверяется рядом с «активный своей метки в ленте есть» | Ревью |
| ПР-7 | Сначала тест должен упасть по правильной причине: из-за отсутствующего поведения, а не из-за ошибки в самом тесте. Красное состояние видно в red-фазе TDD до написания кода | TDD, ревью |

## 5. E2E и браузер

| # | Правило | Контроль |
|---|---|---|
| БР-1 | Элементы ищутся так, как их видит человек: по роли, подписи, тексту из каталога. `data-testid` — только там, где доступного способа нет. CSS-классы и XPath запрещены | Линтер (свои правила для `/e2e`) |
| БР-2 | Каждый участник (гость, админ А, админ Б) работает в своём browser context | Фикстуры |
| БР-3 | Вход через UI только там, где проверяется сам вход. В остальных случаях используется `asAdmin` | Ревью |
| БР-4 | Проверки «вживую» ждут результат с таймаутом не больше 5 секунд и без перезагрузки страницы | Ревью |

## 6. Скорость

| # | Правило | Контроль |
|---|---|---|
| СК-1 | Unit-тест — до 100 мс, весь unit-набор — до 60 секунд | Предупреждение в отчёте `make check`, сборка не падает |
| СК-2 | E2E-сценарий — до 30 секунд, smoke целиком — до 60 секунд | Предупреждение в отчёте. Таймаут, после которого тест падает, — по конфигу раннера |

Медленный тест — это сигнал, что он ходит туда, куда не должен: в сеть, в БД или к реальным таймерам. Предупреждение разбирается на ревью.

## 7. Запрещено

- `skip`, `only`, `markTestSkipped`, `markTestIncomplete` и закомментированные тесты.
- `sleep` и фиксированные ожидания.
- Логика в теле теста (см. ЧТ-4).
- Тест, который зависит от результата другого теста.
- Перехват исключения в тесте ради «зелёного» результата.
- Подгонка проверки под фактическое поведение без правки тест-плана.
