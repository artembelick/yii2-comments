4. Пирамида и наборы

  • unit (Codeception с pcov, Vitest с coverage-v8): классы и JS-модули изолированно, без сети и Redis; в БД ходят только тесты репозиториев, внутри транзакции с откатом. Быстрые и самые многочисленные: держат порог покрытия. Локально в make test-unit и на pre-push, в CI на каждый push. Например, {{test:UNIT-VAL-01}} и {{test:UNIT-JS-WS-05}}.
  • smoke (Playwright): стенд жив — страницы открываются, вход работает, WS подключается, ничего не создаётся. Идёт первым после подъёма стенда и в каждом job CI со стендом: {{test:SMOKE-01}}, {{test:SMOKE-04}}.
  • regression (Codeception REST по HTTP, Playwright для WS-контрактов): зафиксированные контракты — валидация, права, безопасность, идемпотентность, и тест на каждый найденный баг. После smoke, до e2e: {{test:REG-G-13}}, {{test:REG-WS-01}}.
  • e2e (Playwright): путь комментария в настоящем браузере с гостем и несколькими админами в своих browser context. Последним, потому что самый медленный: {{test:E2E-01}}, {{test:E2E-08}}.

Порядок make check — от быстрого к медленному: lint → unit → smoke → regression → e2e, первый красный шаг останавливает цепочку ({{file:Makefile}}). В CI на pull request и push в main то же разбито на jobs: ярус parallel идёт шардами, каждый со своим стендом, pristine и exclusive — одним job ({{file:.github/workflows/ci.yml}}). Масштабируется добавлением шардов: тесты яруса parallel работают только со своими данными.

Код писался double-loop TDD по вертикальным срезам ({{file:docs/adr/0001-double-loop-tdd.md}}): срез начинается с красного приёмочного e2e, внутри него unit и regression идут по одному тесту red → green. Сквозной {{test:E2E-01}} зеленел по шагам от среза к срезу.

5. Техники тест-дизайна

  • Граничные значения. Имя 2–64 символа: 1, 2, 64, 65 в {{test:UNIT-VAL-01}}, 64 и 65 по HTTP в {{test:REG-G-14}} и {{test:REG-G-14a}}. Текст до 2000: 2000 и 2001 в {{test:UNIT-VAL-02}} и {{test:REG-G-16a}}.
  • Классы эквивалентности. Провайдеры невалидных данных, один представитель на класс: тип поля в {{test:UNIT-VAL-08}}, отсутствующее поле и массив вместо строки в {{test:REG-G-19}}.
  • Таблица решений. Порядок ошибок валидации: на поле одна ошибка, тип → обязательность → длина, {{test:UNIT-VAL-09}}.
  • Переходы состояний. Комментарий активен ⇄ удалён, включая повторные переходы: {{test:REG-A-50}}, {{test:REG-A-51}}, {{test:REG-A-52}}, {{test:REG-A-53}}, в браузере {{test:E2E-03}} и {{test:E2E-04}}. Состояния WS-соединения (онлайн, переподключение, отключено) и переходы по кодам закрытия: {{test:UNIT-JS-IND-01}}, {{test:UNIT-JS-WS-04}}, {{test:UNIT-JS-WS-05}}.

6. Трассируемость и проверка тестов

  • Сверка ID в обе стороны. Линтер падает на ID в тесте, которого нет в плане, и на ID плана, который не реализован ни одним тестом ({{file:tools/checks/rules/test-ids.js}}, тесты проверки — {{file:tools/checks/__tests__/test-ids.test.js}}). Поэтому доля в разделе 3 и матрица пути не расходятся с кодом.
  • Проверка тестов мутациями. Каждый новый тест сначала был красным: на отсутствующем поведении или на мутации, внесённой в код руками. Таблицы мутаций с результатами — в комментариях к тикетам {{file:.scratch/comments-system/issues/05-new-comment-live.md}}, {{file:.scratch/comments-system/issues/06-edit-delete-restore.md}}, {{file:.scratch/comments-system/issues/07-session-termination.md}}, {{file:.scratch/comments-system/issues/08-strip-invalid-chars.md}}, {{file:.scratch/comments-system/issues/09-rerun-on-same-stand.md}}, {{file:.scratch/comments-system/issues/10-coverage-gaps.md}}. Например, без экранирования имени в админке краснеет {{test:REG-A-34}}.

7. Стабильность и правила

  • Ярусы. pristine — на пустой БД, которую цель пересоздаёт перед ярусом; parallel — только свои данные, можно параллельно и шардами; exclusive — тесты на общую ленту, порядок и rate limit, строго по одному. Пустая лента — {{test:REG-G-02}}, rate limit — {{test:REG-G-22}}.
  • Уникальные метки. Каждый тест создаёт свои данные с меткой из id прогона TEST_RUN_ID и Faker с seed из имени теста и ищет только их ({{file:e2e/support/tag.ts}}, {{test:UNIT-E2E-TAG-01}}).
  • Seed. Codeception и Vitest идут в случайном порядке, seed печатается, упавший прогон повторяется с тем же seed ({{file:codeception.yml}}, {{file:vitest.config.js}}).
  • Без sleep и без повторов. Фиксированные ожидания запрещает линтер ({{file:tools/checks/rules/no-fixed-waits.js}}), реальное время в тестах — тоже. В Playwright retries: 0: флейк — это баг ({{file:e2e/playwright.config.ts}}).
  • Двойной и повторный прогон. Ночной CI дважды гоняет make check с разными seed и make test-rerun — всё ещё раз на том же стенде с данными прошлого прогона ({{file:.scratch/comments-system/issues/09-rerun-on-same-stand.md}}).
  • Правила тестов ({{file:docs/test-plans/rules.md}}): изоляция, детерминизм, Arrange → Act → Assert без логики в теле, точные проверки, моки только на границах, поиск элементов по роли и подписи. Что можно, проверяет линтер ({{file:tools/checks/rules/no-logic-in-tests.js}}), остальное — ревью каждого среза.

8. Стек

  • Приложение: Yii2 на PHP 8.3, Postgres, Redis (pub/sub событий и rate limit), WebSocket-сервер на Workerman ({{file:composer.json}}).
  • Окружение: Docker Compose, на хосте нужны только Docker и make ({{file:docker-compose.yml}}, {{file:Makefile}}).
  • Тесты: Codeception (unit и REST), Vitest, Playwright, отчёт Allure ({{file:package.json}}, {{file:e2e/package.json}}).
  • Линтеры: phpstan, php-cs-fixer, rector, phpcs, oxlint, oxfmt, tsc, hadolint и свои проверки тестов ({{file:tools/checks/rules/index.js}}).
  • CI: GitHub Actions, страница публикуется на GitHub Pages ({{file:.github/workflows/ci.yml}}).

9. Вне объёма

Нагрузочные тесты, проверку заголовков безопасности, матрицу браузеров (только Chromium) и мутационное тестирование инструментом осознанно не делали.
