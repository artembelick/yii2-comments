1. Итог прогона

{{run}}

В отчёте Allure тесты сгруппированы по набору (unit, smoke, regression, e2e) и по ID из тест-плана. У e2e видны шаги test.step, к падениям приложены trace и скриншоты, например у {{test:E2E-01}}. Тест, который идёт в нескольких jobs CI (smoke — в каждом job со стендом), считается один раз. Тесты своих инструментов (сверка ID, линтер тестов, сборка этой страницы) ID не несут: они отдельной строкой и отдельной группой, вне наборов.

4. Пирамида и наборы

  • unit (Codeception с pcov, Vitest с coverage-v8): классы и JS-модули изолированно, без сети и Redis; в БД ходят только тесты репозиториев, внутри транзакции с откатом. Быстрые и самые многочисленные: держат порог покрытия. Локально в make test-unit и на pre-push, в CI на каждый push. Например, {{test:UNIT-VAL-01}} и {{test:UNIT-JS-WS-05}}.
  • smoke (Playwright): стенд жив — страницы открываются, вход работает, WS подключается, ничего не создаётся. Идёт первым после подъёма стенда и в каждом job CI со стендом: {{test:SMOKE-01}}, {{test:SMOKE-04}}.
  • regression (Codeception REST по HTTP, Playwright для WS-контрактов): зафиксированные контракты — валидация, права, безопасность, идемпотентность, и тест на каждый найденный баг. После smoke, до e2e: {{test:REG-G-13}}, {{test:REG-WS-01}}.
  • e2e (Playwright): путь комментария в настоящем браузере с гостем и несколькими админами в своих browser context. Последним, потому что самый медленный: {{test:E2E-01}}, {{test:E2E-08}}.
  • Порядок и масштаб. make check идёт от быстрого к медленному: lint → unit → smoke → regression → e2e, первый красный шаг останавливает цепочку. В CI на pull request и push в main то же разбито на jobs: ярус parallel идёт шардами, каждый со своим стендом, pristine и exclusive — одним job. Масштабируется добавлением шардов: тесты яруса parallel создают и ищут только свои данные с уникальной меткой ({{test:UNIT-FIX-02}}).
  • Double-loop TDD. Код писался по вертикальным срезам ({{file:docs/adr/0001-double-loop-tdd.md}}): срез начинается с красного приёмочного e2e, внутри него unit и regression идут по одному тесту red → green. Сквозной {{test:E2E-01}} зеленел по шагам от среза к срезу.

5. Техники тест-дизайна

  • Граничные значения. Имя 2–64 символа: 1, 2, 64, 65 в {{test:UNIT-VAL-01}}; текст до 2000: 2000 и 2001 в {{test:UNIT-VAL-02}}. Те же границы по HTTP проверяет regression.
  • Классы эквивалентности. Провайдеры невалидных данных, один представитель на класс: тип поля в {{test:UNIT-VAL-08}}, отсутствующее поле и массив вместо строки в {{test:REG-G-19}}.
  • Таблица решений. Порядок ошибок валидации: на поле одна ошибка, тип → обязательность → длина, {{test:UNIT-VAL-09}}.
  • Переходы состояний комментария. Активен ⇄ удалён, включая повторные переходы: {{test:REG-A-50}}, в браузере {{test:E2E-03}}.
  • Переходы состояний WS-соединения. Онлайн, переподключение, отключено и переходы по кодам закрытия: {{test:UNIT-JS-WS-05}}, {{test:UNIT-JS-IND-01}}.

6. Трассируемость и проверка тестов

  • Сверка ID в обе стороны. Линтер падает на ID в тесте, которого нет в плане, и на ID плана, который не реализован ни одним тестом; ID в комментарии тест не реализует ({{file:tools/checks/__tests__/test-ids.test.js}}). Поэтому доля в разделе 3 и матрица пути не расходятся с кодом.
  • Проверка тестов мутациями. Каждый новый тест сначала был красным: на отсутствующем поведении или на мутации, внесённой в код руками. Таблицы мутаций с результатами — в комментариях к тикетам 05–10 (.scratch/comments-system/issues/). Например, без экранирования имени в админке краснеет {{test:REG-A-34}}.

7. Стабильность и правила

  • Ярусы. pristine — на пустой БД, которую цель пересоздаёт перед ярусом; parallel — только свои данные, можно параллельно и шардами; exclusive — тесты на общую ленту, порядок и rate limit, строго по одному. Пустая лента — {{test:REG-G-02}}, rate limit — {{test:REG-G-22}}.
  • Уникальные метки. Каждый тест создаёт свои данные с меткой из id прогона TEST_RUN_ID и Faker с seed из имени теста и ищет только их ({{test:UNIT-E2E-TAG-01}}).
  • Seed. Codeception и Vitest идут в случайном порядке, seed печатается, упавший прогон повторяется с тем же seed. Данные теста определяет seed Faker из имени: при одном seed и одном id прогона метки совпадают ({{test:UNIT-FIX-02}}).
  • Без sleep и без повторов. Фиксированные ожидания и реальное время в тестах запрещает линтер ({{file:tools/checks/__tests__/no-fixed-waits.test.js}}, {{file:tools/checks/__tests__/no-real-time.test.js}}). В Playwright retries: 0: флейк — это баг.
  • Двойной и повторный прогон. Ночной CI дважды гоняет make check с разными seed и make test-rerun — всё ещё раз на том же стенде с данными прошлого прогона. Второй проход не сталкивается с первым, потому что метка начинается с id прогона ({{test:UNIT-FIX-03}}, {{test:E2E-FIX-01}}).
  • Правила тестов ({{file:docs/test-plans/rules.md}}): изоляция, детерминизм, Arrange → Act → Assert без логики в теле, точные проверки, моки только на границах, поиск элементов по роли и подписи. Что можно, проверяет линтер ({{file:tools/checks/__tests__/no-logic-in-tests.test.js}}, {{file:tools/checks/__tests__/strict-assertions.test.js}}), остальное — ревью каждого среза.

8. Стек

  • Приложение: Yii2 на PHP 8.3, Postgres, Redis (pub/sub событий и rate limit), WebSocket-сервер на Workerman. Схему Postgres сверяет {{test:UNIT-FIX-01}}, WS-сервер — {{test:REG-WS-01}}.
  • Окружение и CI: Docker Compose и make, на хосте нужны только Docker и make; GitHub Actions, страница публикуется на GitHub Pages. Что стенд поднялся, первым в каждом job проверяет {{test:SMOKE-01}}.
  • Тесты: Codeception (unit и REST), Vitest, Playwright, отчёт Allure. Например, {{test:UNIT-VAL-01}} на Codeception и {{test:E2E-01}} на Playwright.
  • Линтеры: phpstan, php-cs-fixer, rector, phpcs, oxlint, oxfmt, tsc, hadolint и свои проверки тестов ({{file:tools/checks/__tests__/cli.test.js}}).

9. Вне объёма

Нагрузочные тесты, проверку заголовков безопасности, матрицу браузеров (только Chromium) и мутационное тестирование инструментом осознанно не делали.
